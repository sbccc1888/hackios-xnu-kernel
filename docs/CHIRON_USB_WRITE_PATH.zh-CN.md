# 写入通路验证：`port: c4 0->0` 不是写失败的证据

一条从早期就写在待办列表最前面的判断是：

> **验证 8 位写入通路是否真的生效**——`port: c4 0->0` 就是写不进的证据
> （写 0x80 读回 0）。如果字节写无效，必须改回 32 位访问。

**这个前提是错的，而答案一直就在日志里。**

---

## 1. 实测数据

`prb.bin`（最后一次成功运行的完整日志）里有这一行：

```
wtest: b90 30->5a w90 30303030->5a5a5a5a b04 13->1a
```

逐项解码：

| 项 | 操作 | 结果 | 结论 |
|---|---|---|---|
| `b90` | 字节写入 `0x90` ← `0x5a` | 读回 `0x5a` | **8 位写入有效** |
| `w90` | 32 位写入 `0x90` ← `0x5a5a5a5a` | 读回 `0x5a5a5a5a` | **32 位写入有效** |
| `b04` | 字节写入 `0x04` ← `0x5a` | 读回 `0x1a` | bit6 只读，其余成功 |

`w90` 读回 `0x30303030` 而不是 `0x30`，正是**字节宽寄存器在 32 位读取时复制单字节**的特征，
说明这个 PHY 的访问模型符合预期，而不是访问失效。

`b04` 的差异可以精确解释：

```
0x5a = 0101 1010
0x1a = 0001 1010
0x5a & ~0x40 = 0x1a          ← 精确吻合
```

**`0x04`（PLL_TEST）的 bit6 是只读或未实现的，写入的其余位全部生效。**
这不是写失败，是一个有只读位的寄存器。

---

## 2. 为什么 `c4 0->0` 不是证据

那一行来自 `chiron_port_powerdown()`：把 `0x80` 写进 `0xC4`，读回 `0`。

但 `0xC4` 是 `UTMI_CTRL2`，而**工作硬件上它本来就是 0**：

```
map2.bin（在 loader 入口抓取，此时 fastboot 的端口还活着）：
  0x0c4  UTMI_CTRL2 = 0x00
```

**它读回 0 是因为固件让它保持 0，不是因为写入失败。**

`0xC4` 很可能写入被忽略，或该位只在 ULPI 模式下有意义。而 `0x90` 的测试证明
**字节写入通路本身是好的**。

---

## 3. 代码早已按正确结论改过

`df2fc71` 已经根据同一份实测数据**停止写 `0xC0`/`0xC4`**：

```
不写：0x22c   0xc0   0xc4
写：  0xb4=0x19   0x210=0x22   0x23c=0x45   0x240=0x09   0x24c=0x90
```

**所以当前代码是对的，只是待办列表里那条判断没人更新。**

---

## 4. 结论

待办列表的前两项都失效了：

| 原待办 | 实际状态 |
|---|---|
| 1. 验证 8 位写入是否生效 | **已验证有效**（`wtest: b90 30->5a`） |
| 2. 若无效，改回 32 位访问 | **不需要** |

**不需要任何代码改动。** 这一节的存在是为了让这条错误前提不再被重新提出。

---

## 5. 方法论

这是今晚第三次因为**没有回头核对已有实测数据**而浪费时间：

1. `map2.bin` 里 `0xc0`/`0xc4` 应为 0 —— 数据在手上很久才被解析
2. `run 0 hlt 1` —— 盯着 `lkst`/`devaddr`，漏看了 `run`/`hlt`
3. **`wtest` 那一行 —— 一直摆在那里，却把它当成“写入失败”**

而 `port: c4 0->0` 这个“证据”被写进待办列表后，**二十五轮里没有人质疑过它**，
包括我自己。

**规则：任何被当作前提的判断，都要能追溯到一行具体的实测输出，并且那条输出要被重新核对一次。**
